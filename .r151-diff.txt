    F1 — MEDIUM. server/src/routes/ingest.ts POST /ingest/sessions now
    enforces the post-seal freeze via a DB-side WHERE clause instead of
    a JS-side snapshot check. Prior shape:
    
      const existing = await db.session.findUnique(...);
      const isSealed = existing?.status === "sealed";
      ...
      db.session.upsert({ ..., update: isSealed ? {} : {full-fields} });
    
    is a TOCTOU race against /ingest/receipts's concurrent seal at
    :~763. If the receipts handler commits `session.update({status:
    "sealed"})` between our findUnique (T0) and the upsert (T1):
    
      1. Our JS snapshot shows existing.status="live", isSealed=false.
      2. Postgres' ON CONFLICT DO UPDATE has no sealed guard.
      3. The row is blindly reverted from "sealed" back to "live" with
         the attacker-supplied agent / workflow / policyVersion /
         closedAt.
      4. Signed receipt.eventCount mismatches session.events; the
         /events guard at :402 stops rejecting further appends; SPA
         and /me/export render the mutated fields.
    
    This is the same post-seal defacement class R119 F2 (metadata
    freeze) / R141 F3 (pre-sealed CREATE) / R144 F1 (pre-sealed UPDATE)
    closed for the non-concurrent paths. R144's own comment named the
    invariant ("Same threat model as R141 F3; the invariant needs to
    hold on UPDATE too") but enforced it only against attacker-
    supplied s.status="sealed" — a race against a legitimate concurrent
    seal slipped through. Threat model: compromised AV_INGEST_TOKEN,
    same as R141 F3 / R144 F1.
    
    Fix moves the guard to the DB WHERE clause via updateMany:
    
      const upd = await db.session.updateMany({
        where: { deploymentId, externalId, status: { not: "sealed" } },
        data: { agent, workflow, status, policyVersion, closedAt },
      });
      if (upd.count === 0) {
        // Row doesn't exist yet (CREATE branch) OR row is sealed
        // (leave it alone). Upsert with update:{} handles both.
        session = await db.session.upsert({..., update: {}, select:...});
      } else {
        session = await db.session.findUnique({..., select:...});
      }
    
    Postgres evaluates `status: { not: "sealed" }` under the same row
    lock the UPDATE takes, so no snapshot can lie about the sealed
    state. R123 F2's "return persisted agent, not caller-supplied
    s.agent" invariant preserved on both branches via the select clause.
    
    F2 — LOW. server/src/lib/webhooks.ts WEBHOOK_SWEEPER_INTERVAL_MS
    now validated via Zod in server/src/env.ts. Prior shape:
    
      const SWEEPER_INTERVAL_MS =
        Number(process.env.WEBHOOK_SWEEPER_INTERVAL_MS ?? 15_000);
    
    is the exact footgun R99 F3 closed for the sibling
    RETENTION_SWEEPER_INTERVAL_MS. Number("") === 0, Number("15s") ===
    NaN, Number("15_000") === NaN (underscores rejected), all of which
    Node's setInterval clamps to ~1 ms — the sweeper fires every
    event-loop tick and hammers Postgres with the FOR UPDATE SKIP LOCKED
    claim UPDATE. Not attacker-triggered (ops-config typo only), but the
    retention sibling got the full guard for the same failure mode and
    this one was missed.
    
    Fix adds env.WEBHOOK_SWEEPER_INTERVAL_MS: z.string().default("15000")
    .transform(Number).refine((n) => Number.isInteger(n) && n >= 1_000
    && n <= 300_000) with docstring mirroring the retention entry.
    Bounds: 1 s floor (retry latency ceiling — anything slower starves
    customer endpoints on failed deliveries), 5 min ceiling (safety net
    so operators don't silently disable retries by setting it enormous).
    lib/webhooks.ts imports the validated value:
    `const SWEEPER_INTERVAL_MS = env.WEBHOOK_SWEEPER_INTERVAL_MS;`.
    
    Grep for `Number(process.env.` across server/src now returns only
    comment matches — no live sites remain.
